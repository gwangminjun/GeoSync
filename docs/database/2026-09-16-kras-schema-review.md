# KRAS DB 설계 재점검

검토일: 2026-09-16  
대상: [설계서](../superpowers/specs/2026-09-11-kras-database-sync-design.md), [생성 SQL](./kras-schema-create.sql), [실행 안내](./kras-schema-create.md)

## 판단

신규 `kras` 스키마, PNU 중심 조회, 원본/업무/API 응답 분리, 공간 데이터 버전 게시라는 방향은 유지할 수 있다. 다만 현재 DDL을 **운영 반영 규칙까지 완성된 설계로 보기는 어렵다.** 정상 경로에서 스키마가 생성되는 것과 잘못된 수집 결과가 게시되지 않는 것은 별도 검증이다.

새 임시 PostgreSQL 16.14/PostGIS 3.6.2 DB에 현재 SQL을 다시 적용했고, 아래 네 가지를 재현했다. 생성 SQL 자체는 수정하지 않았다. 재현 코드는 [kras-schema-review-repro.sql](./kras-schema-review-repro.sql)에 있다. 테스트 행은 ROLLBACK했고 운영 DB에 접속하지 않았다.

P1은 조회 결과의 완전성·정상성을 해치는 게시 경로, P2는 적재 정합성·재시도 보장 공백으로 구분했다. 아래 항목은 실제 운영 장애가 발생했다는 뜻이 아니라, 현재 SQL이 받아들이는 잘못된 상태를 확인한 것이다.

## F1 — P1: 오류 응답도 정상 API 게시 집합에 들어갈 수 있음

근거: 생성 SQL 1534~1555행 `api_response`, 1559~1572행 `api_bundle`, 3935~3941행 `api_current_response`.

`response_xml`은 XML 문법만 검사한다. `source_result_code`에 성공값 제약이 없고, `api_current_response`는 bundle의 상태와 `is_complete`만 확인한다. 수집 item의 실패 여부·응답 검증 결과·필수 구성원 수는 확인하지 않는다.

재현 결과:

- `sync_item.status=FAILED`인 item을 생성.
- `<CODE>9999</CODE>` XML을 `source_result_code=9999`, `data_state=COLLECTED`로 저장.
- `is_complete=true`, `status=PUBLISHED`인 bundle에 넣고 활성화.
- `api_current_response`에서 오류 응답 1건 조회됨.

실행 안내에서 외부 성공 코드 검증을 배치에 위임한다고 명시한 것은 확인했다. 따라서 현재 DB가 그 검증까지 보장한다고 해석하면 안 된다. 아직 해당 배치 구현이 없고, 게시를 위한 검증된 단일 진입점도 없다는 것이 남은 설계 문제다.

수정 방향:

1. 원본 오류 응답은 원본 계층에만 두고 API 게시 후보에는 서비스별 계약을 통과한 응답만 등록한다. 서비스마다 성공/정상 빈 응답 규칙을 정의한다.
2. bundle별 필수 서비스·bno·옵션 목록을 게시 시점에 고정하고 실제 구성원과 대조한다. 임의의 boolean만으로 완전성을 선언하지 않는다.
3. 잠금→응답/구성원 검증→bundle 완료→활성 포인터 변경을 하나의 게시 함수 또는 단일 애플리케이션 트랜잭션으로 구현한다. 직접 상태 변경을 제한하고 실패하면 이전 게시 버전을 유지한다.
4. 게시 응답·구성원을 불변 버전으로 관리한다. 후속 업데이트가 같은 bundle의 조회 결과를 바꾸지 못하도록 한다.

단순히 조회 뷰에서 오류 행을 제외하는 것만으로는 조합 API의 구성원 누락을 해결할 수 없다.

## F2 — P1: 용도지역 release가 부분 자료로 노출될 수 있음

근거: 생성 SQL 1731~1760행 `spatial_release`/member/publication, 3924~3933행 `lt_c_uzone`.

현재 뷰는 release 전체를 검사하지 않고 각 item이 SUCCESS인지 필터링한다. release의 상태를 PUBLISHED로 바꿀 때 모든 레이어의 성공을 검증하는 제약/게시 절차가 없다. release가 완전하다는 기대 목록도 DB에 고정되지 않는다.

재현 결과: 같은 release에 SUCCESS 레이어 A와 FAILED 레이어 B를 넣고 게시하면, 오류 없이 A만 1건 조회된다. 지도 소비자는 B가 원래 없었던 것인지 동기화 실패인지 구별할 수 없다.

수정 방향:

- 수집 시작 당시의 기대 레이어 목록과 정상 0건 레이어를 manifest로 보존한다.
- 기대 목록 대비 구성원 일치, 모든 필수 item의 완료, 기관·dataset·scope·레이어 일치, 도형 검증을 통과한 release만 활성화한다.
- 한 레이어라도 실패하면 기존 기관 전체 release를 유지한다. 새 release의 성공 레이어만 대체하지 않는다.
- 활성 release/member/item은 게시 후 변경하지 않는다.

현행 뷰의 행별 SUCCESS 필터는 방어 장치로 남길 수 있지만, 전체 release 게시 검증을 대신하지 못한다.

## F3 — P2: 업무 데이터의 수집 출처에 기관 일치 제약이 없음

근거: 생성 SQL 223행 `parcel.source_item_id`, 250행 `land_basic.source_item_id`와 다른 업무 테이블의 동일한 FK 패턴.

실행과 API 응답에는 복합 FK로 기관을 검증하지만 업무행은 `source_item_id → sync_item(item_id)`만 참조한다. 필지 기관/PNU 검사와 수집 item의 기관 검사가 연결되어 있지 않다.

재현 결과: `org_cd=46870`인 필지와 토지기본정보가 `org_cd=27170`의 수집 item을 참조해 저장되고, `land_frst_ledg`에 정상 조회된다. 수집 item 기준 복구·대사·기관별 감사에서 출처가 뒤섞일 수 있다. 단일 DB를 쓰는 것과 기관별 출처가 일치하는 것은 별개다.

수정 방향:

- 업무 루트 행에 `org_cd`를 두고 `(source_item_id,org_cd)` 복합 FK를 사용한다. 필지 업무행은 `(pnu,org_cd)`도 필지 마스터와 일치시킨다.
- 자식 행은 부모의 기관과 같은 source item에 속하는지 검증한다. `last_seen_item_id`에도 같은 범위 규칙을 적용한다.
- 데이터셋과 업무 테이블의 대응은 별도의 수집 어댑터 계약으로 검증한다. 기관 일치만 추가해도 다른 서비스 item의 잘못된 연결은 남는다.

## F4 — P2: 변동 이벤트의 NULL 행 번호가 중복 제약을 우회함

근거: 생성 SQL 676행 `UNIQUE(source_item_id,record_no)`, 682행 `record_no bigint CHECK(record_no > 0)`.

`record_no`에 NOT NULL이 없어서 동일 item과 동일 payload를 행 번호 없이 여러 번 적재할 수 있다. 이는 원본 내 `(item_id,record_no)` 식별이라는 설계 의도와 다르다.

재현 결과: 같은 item·토지이동순번·payload_hash를 갖고 `record_no=NULL`인 행 2개가 모두 저장됐다.

수정 방향:

- `land_change_event.record_no`를 NOT NULL로 변경한다.
- 원본 레코드를 반드시 먼저 적재하는 방식이면 `(source_item_id,record_no)`를 `sync_record(item_id,record_no)`에 연결한다.
- 이 제약은 **동일 item 내 중복**만 막는다. 새 item을 만든 재시도와 중복 기간 재조회는 별도 이벤트 정규화/업무 반영 멱등성 규칙이 필요하다. `LAND_MOV_NO`가 전역 고유하다고 가정한 UNIQUE는 추가하지 않는다.

## 추가로 확정해야 할 설계 선택

다음은 이번 재현에서 오류로 확정한 항목과 구분한다.

### 반복 데이터의 교체 단위와 ID 수명

건물·대지권 등 자연키 미확정 테이블에서 surrogate ID를 쓰는 선택은 타당하다. 그러나 독립 서비스 수집 때 부모를 삭제·재생성하면 다른 서비스가 적재한 자식 FK와 충돌할 수 있다. `building_register`를 새 ID로 교체하면서 기존 `building_title`을 보존하는 방식은 그대로 실행할 수 없다.

서비스별로 안정적인 부모 ID를 유지할지, 하나의 전체 의존 집합을 버전별로 만들지 결정해야 한다. 원천 키 확인 전에는 전체 집합 버전 방식이 명확하지만 조회·보존비용이 늘어난다. 대량 CASCADE 삭제로 이 문제를 덮지 않는다.

### 102개 테이블과 중복 저장 비용

102개 중 39개는 업무별 stage다. 이 수 자체가 오류는 아니지만 초기 조회 API 대체에 전부 필요한지는 다시 좁힐 수 있다. 원본 파일·JSON·정규화 업무행·XML 응답·도형 원본/투영이 중복 저장되므로 필지/건물/도형 수와 보존기간으로 용량을 산정해야 한다.

XML 응답은 기존 API 호환에 필요한 구조를 보존하므로 일괄 제거하지 않는다. 실제 검색/조인할 컬럼을 우선 정규화하고, stage는 성능·검증 요구가 있는 데이터셋부터 운영하는 방안을 검토한다. 원본 item FK 때문에 기록을 무조건 기간별 삭제할 수 없으므로 삭제 순서와 보존 참조도 정해야 한다.

### 수집 키와 요청 호환

`scope_key varchar(256)`, `entity_key varchar(512)`에 동·층·호·실 원문을 그대로 이어 붙이면 각 varchar(150) 규격 전체를 수용하지 못할 수 있다. 전유부 ID 또는 정규화 요청 해시를 쓰고 원문 파라미터는 JSON에 두는 규칙을 명확히 한다.

현재 컨트롤러는 빈 PNU를 허용하지만 신규 API 응답 테이블은 PNU를 필수 FK로 요구한다. 사용자가 목표로 한 정상 PNU 조회는 가능하나, 기존의 모든 요청 조합을 호환한다고 선언하려면 빈 PNU의 실제 사용 여부·응답과 지도 크기/축척 옵션을 확인해야 한다.

### 검증되지 않은 규격

HWP에 없는 기존 KRAS/KOREPS 서비스는 mock 구조로만 확정할 수 없다. 날짜·면적·반복 계층·식별자·정상 빈 응답을 운영 샘플로 대조해야 한다. 기존 문서의 UNVERIFIED/비활성 시작 정책은 유지하는 것이 맞다.

## 권장 작업 순서

1. API bundle과 공간 release의 완전성 정의·게시 트랜잭션을 먼저 확정한다.
2. 업무 출처 기관 FK와 이벤트 행 번호 제약을 보완한다.
3. 반복 데이터의 부모 ID 수명·교체 범위·기간 중복 처리 규칙을 확정한다.
4. 실패한 새 버전을 게시하지 않고 이전 버전을 유지하는 테스트, 게시 동시 조회, 게시 후 불변성 테스트를 추가한다.
5. 실제 서비스 샘플과 기관별 데이터량으로 컬럼·테이블 수·보존기간을 조정한다.

이번 검토는 DDL과 설계의 검토 결과다. 운영 응답 대조·성능·실제 배치 구현·권한 정책까지 검증한 것은 아니다.
