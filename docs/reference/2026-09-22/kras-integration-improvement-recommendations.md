# KRAS 신규 연계 메뉴 기능 추가 및 개선 제안

- 작성일: 2026-09-22
- 대상: `kras 적재(신규)` 메뉴, `/kras-db`
- 문서 성격: 현재 구현에 근거한 개선 제안. 구현 완료 내역이나 확정 설계가 아니다.
- 검토 범위: 화면 템플릿, 컨트롤러, 수집·승격 서비스 및 프로젝트 참고 문서
- 검토 한계: 코드 기준으로 확인했으며, 실제 서버 실행·운영 DB 검증·테스트 실행은 하지 않았다.

## 1. 현재 제공하는 기능

| 구분 | 현재 기능 |
|---|---|
| 공간 데이터 | 연속지적 SHP 수집 및 public 반영, 용도지역 카탈로그 수집·레이어 순회·릴리즈 발행·public 반영 |
| 전체 파일 | 토지기본정보 TXT 수집 및 업무 테이블 반영, 공시지가 TXT 수집 |
| XML 연계 | PNU 단건 수집, 기간별 수집, 파싱 결과 미리보기, 업무 테이블 반영 |
| 검증 관리 | 데이터셋별 VERIFIED 전환, 활성화 및 검증 원복 |
| 상태 확인 | 연속지적 최근 실행 이력, 일부 건수 비교, 용도지역 최신 릴리즈·레이어 상태 |

수집과 운영 테이블 반영을 분리하고, DB 가드에서 검증 상태·데이터 완전성 등을 확인하는 구조는 유지하는 것이 좋다. 공시지가 전체 TXT처럼 별도 승격 단계가 없는 경로도 있으므로 모든 데이터셋에 동일한 단계를 강제하지 않는다.

현재 기능 범위는 화면 상단의 “연속지적 1단계” 설명보다 넓다. 운영자가 필요한 연계를 찾고, 준비 상태를 확인하고, 실패한 작업을 복구할 수 있도록 화면과 이력을 보강하는 것이 우선이다.

## 2. 우선순위별 개선 제안

우선순위 1은 운영 상태 확인과 복구에 직접 필요한 항목, 2는 사용성과 검증 품질 개선, 3은 운영 자동화 확장이다.

| 우선순위 | 기능 | 현재 상태 | 개선 방향 |
|---|---|---|---|
| 1 | 전체 연계 작업 이력 및 이어하기 | 일반 실행 이력 표는 연속지적만 표시한다. PNU·기간·TXT 반영 대상 ID는 화면 메모리에 보관한다. | 전체 데이터셋의 수집·실패·반영 이력을 통합하고, 이전 수집 건을 선택해 미리보기와 반영을 이어간다. |
| 1 | 실행 전 준비 상태 검사 | 검증 상태, 필수 입력, 선행 데이터 등 일부 조건을 실행 후 오류로 알게 된다. | 실행 전에 조건을 점검하고 불가 사유와 해결 방법을 표시한다. |
| 1 | 비동기 실행 및 진행 상태 조회 | 요청이 끝날 때까지 화면에 실행 중 메시지를 표시한다. | 작업 ID를 먼저 반환하고 다운로드·파싱·저장 단계, 처리 건수, 경과 시간을 조회한다. |
| 2 | 목록·상세 중심의 화면 구성 | 다수의 검증·수집 카드가 한 페이지에 나열된다. | 토지·건물·공간·가격 분류, 검색, 상태 필터를 제공하고 개별 연계의 상세 화면에서 작업한다. |
| 2 | 운영 반영 전 변경 내용 비교 | JSON 미리보기와 일부 테이블의 건수 비교를 제공한다. | 기존/신규 건수, 증감률, 추가·변경·제거 예상 건수와 샘플을 보여준다. |
| 2 | 검증 근거 관리 | 검증 버튼은 사용자의 확인을 DB 상태에 반영한다. | 검증 일시·담당자·응답 샘플·매퍼 버전을 기록하고 검증 진행 상황을 관리한다. |
| 2 | 부분 실패 표시 및 복구 안내 | 용도지역 순회 결과에 실패 레이어가 있어도 요청 결과는 성공으로 표시될 수 있다. | 완료·일부 실패·실패를 구분하고 실패 사유 및 재시도 방법을 유지한다. |
| 3 | 입력 도우미와 연계 순서 안내 | 추가 파라미터를 JSON으로 직접 입력하는 방식이 있다. | 서비스별 입력 폼과 선행 조회 결과 선택을 제공한다. |
| 3 | 신규 경로 전용 예약·다건 수집 | 신규 적재 경로는 기존 스케줄과 분리된 수동 실행 중심이다. | 검증된 서비스부터 PNU 목록·기간 분할·예약 수집을 추가하고 속도 제한·재시도·재개를 함께 설계한다. |

## 3. 먼저 개선할 구체적인 동작

### 3.1 새로고침 후 반영 대상 선택 복구

`kras-db.html`은 PNU·기간·TXT 수집의 작업 ID를 각각 `pnuItemIds`, `rangeItemIds`, `txtItemIds`라는 JavaScript 변수에 보관한다. 페이지를 새로고침하면 이 선택 정보가 사라져 이전 수집 건의 반영을 화면에서 이어가기 어렵다.

권장 동작:

- DB 이력에서 수집 완료 및 반영 가능 작업을 조회한다.
- 데이터셋별로 작업 ID, 대상 PNU 또는 기간, 수집 시각, 경고 유무를 표시한다.
- 선택한 작업의 미리보기를 다시 조회하고 반영한다.
- 반영 가능 여부는 서버에서 재검사한다.

### 3.2 수집 실패 이력 보존

`KrasPnuIngestService`는 작업 이력 생성, 외부 API 호출, 파싱 및 stage 적재를 같은 트랜잭션 안에서 처리한다. 예외가 발생하면 해당 트랜잭션이 롤백되므로 그 안에서 생성한 작업 이력도 함께 사라진다. 오류 로그는 남지만 DB 작업 이력만으로 실패를 추적하기 어렵다.

권장 동작:

- 작업 실행 기록과 데이터 적재 트랜잭션을 분리한다.
- 실패 단계, 오류 요약, 시도 횟수, 시작·종료 시각을 남긴다.
- 실패 이력에서 동일한 입력 조건으로 재시도할 수 있게 한다.
- 다른 수집 경로도 동일한 문제가 있는지 구현 단계에서 확인한다.

### 3.3 용도지역 부분 성공 표현

`KrasUsezoneIngestService.runLayerSweep()`는 레이어별 성공·실패 결과를 반환하고, 이미 완료된 레이어는 재사용한다. 컨트롤러는 순회가 반환되면 실패 레이어가 포함되어도 `success: true`를 반환한다. 화면은 이를 성공 색상으로 표시하고 자동 새로고침한다.

권장 동작:

- 전체 완료, 일부 실패, 전체 실패를 구분한다.
- 성공·실패·재사용 건수를 각각 표시한다.
- 실패 레이어와 사유를 재조회할 수 있도록 저장한다.
- 기존 완료 레이어 재사용 로직을 활용해 “미완료 레이어 재시도” 동작을 명확히 안내한다.
- 릴리즈 발행 시 DB의 전체 완전성 검증은 유지한다.

### 3.4 메뉴명과 안내 문구 정리

상단 설명은 현재도 “연속지적 1단계”로 되어 있다. 실제 제공 기능에 맞춰 다음과 같이 정리하는 것을 추천한다.

| 현재 표현 | 권장 표현 |
|---|---|
| kras 적재(신규) | KRAS 연계 관리 |
| 연속지적 1단계 | 토지·건물·공간·가격 데이터 수집 및 반영 관리 |
| 업무 테이블로 승격 | 업무 테이블 반영 |
| public 승격 | 지도 서비스 반영 |
| VERIFIED / UNVERIFIED | 검증 완료 / 검증 필요 — 상세에서 기술 상태값 병기 |

## 4. 실행 전 점검 및 검증 관리

실행 버튼 주변에서 다음 항목을 확인할 수 있도록 한다.

| 점검 항목 | 사용자에게 보여줄 내용 |
|---|---|
| 데이터셋 검증·활성화 | 검증 완료 여부, 비활성 사유, 검증 절차 연결 |
| 서비스 ID | 설정 여부 및 미확정 시 필요한 조치 |
| 필수 입력값 | PNU 형식, 기간, 건물식별번호 등 누락·형식 오류 |
| 선행 데이터 | 선행 조회 또는 업무 테이블 반영 필요 여부 |
| 연결·저장 환경 | 대상 DB와 필요한 스키마·테이블 준비 여부, 연결 점검 결과 |
| 작업 상태 | 실행 중인 작업, 반영 가능한 수집 건, 재시도 가능한 실패 건 |

서비스 카탈로그와 코드에는 응답 태그를 가설로 정의한 선언형 매퍼 14개가 있다. 코드 구현 여부와 실제 응답 검증 완료 여부를 분리해서 표시해야 한다. 검증 완료 전환 버튼 자체가 응답 검증을 수행하는 것은 아니므로, 확인한 응답과 매퍼 버전을 연결해 근거를 남기는 것이 좋다.

실행 전 점검은 DB 가드를 대체하지 않는다. 실행 직전과 실제 반영 시점에도 서버 및 DB 검증을 유지한다.

## 5. 진행 상태와 반영 미리보기

### 5.1 진행 상태

장시간 실행을 별도 작업으로 관리하고 화면에서 작업 상태를 조회하도록 개선한다. 데이터셋별 실제 처리 단계에 맞춰 다운로드, 파싱, 임시 저장, 검증, 반영 대기 또는 완료를 표시한다.

처리 총량을 알 수 없는 단계는 임의의 진행률 대신 현재 단계·처리 건수·경과 시간을 보여준다. 새로고침이나 서버 재시작 이후의 상태 복구, 중단된 작업 식별도 함께 설계한다.

### 5.2 반영 전 비교

- 대상 기관, 데이터셋, 작업 ID 및 반영 대상 테이블
- 현재 건수와 수집 건수, 증감률
- 반영 방식에 따른 추가·변경·제거 예상 건수와 변경 샘플
- 파싱 경고, 제외 레코드 및 반영 차단 사유

공간 데이터의 public 반영에는 0건 또는 기존 대비 50% 미만으로 급감한 경우 차단하는 DB 함수가 이미 있다. 이 조건을 사전 안내에 활용하되 최종 DB 검사는 유지한다. 데이터셋마다 UPSERT, 범위 교체, 추가 전용 등 반영 방식이 다르므로 비교 기준도 해당 방식에 맞춰야 한다.

## 6. 권장 진행 순서

### 1차: 이력과 복구 중심

1. 전체 데이터셋 작업 이력 및 실패 기록을 정리한다.
2. 이전 수집 건 선택, 미리보기 재조회, 반영 이어하기를 제공한다.
3. 실행 전 조건 점검과 불가 사유 안내를 추가한다.
4. 용도지역 부분 실패 표시와 재시도 안내를 개선한다.
5. 메뉴명과 현재 범위에 맞지 않는 문구를 정리한다.

### 2차: 작업 가시성과 사용성

1. 비동기 실행 및 진행 상태 조회를 도입한다.
2. 목록·상세 화면, 검색 및 상태 필터를 구성한다.
3. 검증 근거 기록과 운영 반영 전 비교를 보강한다.

### 3차: 검증된 연계 자동화

1. 서비스별 입력 도우미와 선행 조회 연결을 제공한다.
2. PNU 다건·기간 분할·예약 수집을 추가한다.
3. 요청 속도 제한, 실패 재시도, 중단 후 재개를 함께 제공한다.

초기 자동화는 검증된 서비스의 수집부터 적용하고, 운영 테이블 반영은 별도 단계로 유지하는 것을 추천한다.
