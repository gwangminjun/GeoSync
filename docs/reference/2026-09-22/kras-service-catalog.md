# KRAS/KOREPS 서비스 ID 카탈로그 — 어떤 데이터가 어디에 있나

작성일: 2026-09-22 (갱신: 선언형 매퍼 14개 구현 반영)

이 프로젝트가 **실제로 아는** 서비스 ID를 번호순으로 모았다. 출처는 세 곳뿐이다:
`docs/reference/2026-09-18/kras.md`(연계 규격서 §1~16), `kras.sync_dataset` 시드(DDL),
`api-test.html`/`GatewayPaths`의 API 목록. **세 곳 어디에도 없는 번호는 "모른다"고만 적는다** —
추측해서 채우지 않는다.

관련 문서: [구현 구조](./kras-ingest-structure.md) · [계약 검증 런북](./kras-contract-verification-runbook.md)

---

## 1. 한눈에

| 구분 | 개수 |
|---|---|
| 확인된 서비스 ID | **24개** (KRAS 19 + KOREPS 5) |
| 그중 코드 구현 완료 | **24개 전부** — 아래 두 상태로 나뉜다 |
| — 태그명까지 검증된 것 (kras.md에 실제 XML 있음) | **10개** |
| — 코드는 있지만 태그명이 가설인 것 (`KrasSpecMapper` 선언) | **14개** |
| 규격은 있는데 서비스 ID를 몰라 아직 호출 자체가 안 되는 것 | **7개** |

**막힌 빈틈은 이제 한 방향뿐이다.** 이전엔 "ID는 아는데 응답을 모르는 것"(14개)과
"응답은 아는데 ID를 모르는 것"(7개) 두 방향이었는데, 14개는 태그명을 가설로 채워 코드를
전부 만들었다 — 이제 남은 건 그 가설을 실응답으로 확인하는 일(검증)과, ID 자체가 없는 7개뿐이다.

## 3. 🧩 구현됨·태그명 미검증 — 14개

conn_svc_id와 요청 파라미터는 **이미 확인된 값**이다(`GatewayPaths` + `KrasApiClient`,
`/conn` 경로가 운영에서 실제로 도는 중). 막혀 있던 건 응답 XML 구조뿐이었는데, 업무 테이블
컬럼명이 다른 서비스들에서 "KRAS 태그를 소문자로 옮긴 것"이라는 규칙이 성립하길래 그 규칙으로
태그명을 유추해 `KrasSpecMapper`(`KrasSpecMapperConfig`)로 코드를 전부 만들었다.

**단, 태그명은 가설이다.** 실제 운영 응답으로 확인하기 전에는 `VERIFIED`로 올리면 안 된다.
가설이 틀리면 수집 시 예외가 뜨면서 응답에 실제로 있던 태그 목록을 알려주므로, 한 번 호출해 보면
정답을 바로 알 수 있다 — 그래서 "벤더 확인 필요"가 아니라 "검증 필요"로 분류를 바꿨다.

| dataset_code | 서비스명 | 승격 대상 | 선행 필요 |
|---|---|---|---|
| `use_zone` | 용도지역지구 | `land_use_zone` | — |
| `land_use_plan_attr` | 토지이용계획 속성 | `land_use_attribute` | — |
| `land_use_plan_info` | 토지이용계획 + 행위제한 | `land_use_plan`, `land_use_restriction` | — |
| `bldg_dong_info` | 건물 동 정보 | `building_register` | — (건물 계열의 관문) |
| `bldg_ledg_gen_hds_info` | 건축물대장 총괄표제부 | `building_summary` | — |
| `bldg_ho_info` | 건물 호(전유) | `building_unit` | bldg_gbn_no 필요 |
| `bldg_hds_info` | 건축물대장 표제부 | `building_title` + 층별/소유자/변동 | `bldg_dong_info`, bldg_gbn_no |
| `cbldg_hds_info` | 집합건물 표제부 | `building_title`(출처 구분) | `bldg_dong_info`, bldg_gbn_no |
| `cbldg_dfhs_info` | 집합건물 전유부 | `building_exclusive` + 면적/소유자/가격 | `bldg_ho_info`, bldg_gbn_no |
| `land_jiga` | 공시지가(KOREPS) | `koreps_land_price` | — |
| `house_info` | 개별주택가격(KOREPS) | `house_price` | — |
| `fin_dec_jiga` | 공시결정지가(KOREPS) | `final_land_price` | — |
| `read_dec_jiga` | 열람결정지가(KOREPS) | `read_land_price` | — |
| `land_attr` | 토지속성(KOREPS) | `land_attribute` | — |

"bldg_gbn_no 필요"인 4개는 그 값을 **`bldg_dong_info` 응답에서 스스로 얻는다** — 외부 확인이
필요 없다. `land_use_plan_info`(KRAS000026)는 지도/범례 이미지도 함께 오지만, 인코딩·태그를
실응답으로 확인하기 전이라 `land_use_plan`/`land_use_restriction` 두 테이블만 채운다
(`land_use_plan_asset`는 미착수).

## 4. 🚫 ID가 없어 아직 호출 자체가 안 되는 것 — 7개

kras.md에 요청 항목·응답 XML·샘플까지 다 있어 **매퍼와 승격 로직은 이미 완성**돼 있다.
`connSvcId()`가 예외를 던져 실제 호출만 막혀 있다 — 여기는 태그명 문제가 아니라 진짜 ID가 없다.

| kras.md | 서비스명 | 핵심 데이터 | dataset_code |
|---|---|---|---|
| §4 | 대지권등록부(건물조회) | **집합건물 동 목록 + 집합건물순번** — 드릴다운의 출발점 | `collective_building` |
| §5 | 대지권등록부(전유부조회) | **전유부 동/층/호/실** | `collective_unit` |
| §6 | 대지권등록부 | **대지권 비율 + 소유권 연혁** (두 반복 그룹) | `land_right` |
| §9 | 집합건물소유권연혁 | 집합건물 소유권 변동 이력 | `unit_ownership_history` |
| §10 | 토지이동 변동내역 | **기간 내 토지이동 사건**(전/후 지번·지목·면적) | `land_change` |
| §13 | 건물통합정보 | **건물명·용도·구조·면적·층수 + 관련지번** | `integrated_building` |
| §14 | 건물통합도면 | 건물 배치도 이미지(base64) | `building_image` |

### §11·§12는 문서 자체가 잘못돼 있다

| kras.md | 서비스명 | 상태 |
|---|---|---|
| §11 | 소유권 변동내역 | **§10과 내용이 완전히 동일하게 중복 기재됨** — 필드명은 물론 샘플 응답값(`LAND_MOV_NO=27170012014200001800010001`)까지 같다 |
| §12 | 집합건물소유권 변동내역 | 위와 같음 |

복사-붙여넣기 오류로 보인다. 실제 응답을 받아야 진짜 구조를 알 수 있어 **구현하지 않았다**.

## 6. 중요도 관점 정리

### 지금 다 되고 검증까지 끝난 것 — 토지 기본 계열
`KRAS000002`(대장) + `KRAS000003`(공유인) + `KRAS000006/7`(이력) + `KRAS000040`(전체 필지)
+ `KRAS000038`(도형) + `KRAS000039`(전체 지가).
**"필지가 무엇이고, 누구 것이고, 어떻게 변해왔고, 어디에 있고, 얼마인가"는 전부 수집 가능하다.**

### 코드는 다 됐고 실응답 검증만 남은 것 — 건축물대장 + 토지이용 + KOREPS 계열
`KRAS000014/15/16/17/102/103`(건물, 13개 업무 테이블), `KRAS000025/26/27`(토지이용),
KOREPS 5종. **태그명 가설을 실응답으로 맞추는 작업만 남았다** — 새 코드는 필요 없다.
건물 계열은 `bldg_dong_info`(KRAS000102)부터 검증해야 한다 — 나머지 4개가 여기서
파생되는 `bldg_gbn_no`에 의존한다.

### 여전히 막힌 것 — 집합건물(대지권등록부) 계열 + 변동내역 + 건물통합
§4~6·9·10·13·14는 반대로 **규격은 있는데 ID가 없다.** 매퍼·드릴다운 승격까지 완성돼 있어
서비스 ID 7개만 받으면 바로 켤 수 있다. 유일하게 담당자 확인 없이는 진행이 안 되는 구간이다.

## 7. 담당자에게 요청할 것 (이 문서의 실질적 결론)

1. **서비스 ID 7건** — kras.md §4·§5·§6·§9·§10·§13·§14에 해당하는 `conn_svc_id`
   (이 문서 §4 전체가 여기 하나로 좁혀진다 — 나머지는 이미 코드가 있다)
2. **kras.md §11·§12 정정본** — §10과 중복 기재된 문제
3. (참고) KRAS000001, 004~005, 008~013, 018~024, 028~036, 041~100 번호대에 우리가 모르는
   서비스가 더 있는지 — 현재 전체 목록을 받아본 적이 없다

14개(🧩)는 담당자 확인 없이 `/api-test`로 자체 검증 가능하다 — 절차는
[계약 검증 런북](./kras-contract-verification-runbook.md) 참고.
