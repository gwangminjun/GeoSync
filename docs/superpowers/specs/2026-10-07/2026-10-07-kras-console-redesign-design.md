# KRAS 연계 관리 — 첫 화면 재구성 설계

작성일: 2026-10-07
상태: **설계안(미구현)**. 결정 사항 3개가 확정되어야 구현을 시작한다 (8절).

---

## 1. 목적

`/kras-db` 첫 화면을 **운영 상태를 한눈에 보는 화면**으로 바꾼다. 확인하고 싶은 것은 다음과 같다.

1. 각 데이터셋이 DB에 **정기적으로 적재되는지** (스케줄 설정 여부)
2. **다음 실행 시각**은 언제인지
3. **마지막 적재**는 언제, 결과는 어땠는지
4. KRAS API를 **지금 호출해 보면** 응답이 오는지 (API 테스트)

통계와 계약 검증 카드는 첫 화면에서 뺀다.

## 2. 현재 첫 화면의 문제

| 현재 요소 | 문제 |
|---|---|
| 통계 카드 (`krasCount`, `publicCount`, `uzoneKrasCount`, `landBasicCount`, `landPriceFileRowCount`) | 운영 판단과 무관한 숫자가 위쪽을 차지함 |
| 데이터셋별 계약 검증 카드 (VERIFIED 전환 폼) | 데이터셋마다 긴 폼이 있어 상태를 한눈에 못 봄 |
| 스케줄 정보 | 화면 어디에도 없음. 신규 적재 경로는 실제로 스케줄이 없는데 그것도 보이지 않음 |
| 마지막 실행 / 다음 실행 | 데이터셋 단위로 보이지 않음 (`recentRuns`는 최근 목록만) |
| API 테스트 | 별도 `/api-test` 페이지로 이동해야 함 |

## 3. 현재 사실 (코드 확인)

- **스케줄 (기존 경로)**: `kras.schedule` 04:30 (KrasWorker, public·ods 전체 재적재), `ods.schedule` 05:30, `kras.file-download.schedule`은 설정 시 동작. `DynamicScheduleManager`가 cron을 관리하고 `CronExpression.next()`로 다음 실행 시각을 계산할 수 있다.
- **스케줄 (신규 `/kras-db` 경로)**: 없음. 모든 적재는 버튼으로 수동 실행한다. 3차 계획에 예약 수집이 포함되어 있지만 아직 구현되지 않았다.
- **마지막 실행**: `kras.sync_run` / `kras.sync_item`에 기록된다. `KrasOperationLogService`가 실행 로그를 남긴다.
- **API 테스트**: `/api-test` (`ApiTestController`). 데이터셋 목록과 호출 버튼이 있다.
- **계약 검증**: `kras.sync_dataset.contract_status`를 `UNVERIFIED → VERIFIED`로 바꾸는 수동 폼이다 (담당자·응답 샘플·매퍼 버전 기록). `VERIFIED`이고 `enabled=true`여야 수집이 허용된다 (`readiness` 검사).

## 4. 제안 구조

### 4.1 첫 화면: 연계 운영 현황 (`/kras-db`)

한 줄 = 데이터셋 하나. 열 구성:

| 열 | 내용 | 데이터 출처 |
|---|---|---|
| 규격 § / 항목 | 16개 규격 항목 + 파일 데이터셋 | 기존 `SPEC_ITEMS` (임시), 이후 레지스트리 |
| 적재 스케줄 | "없음" / cron 표현식 / "수동" | 신규: 데이터셋별 스케줄 설정 |
| 다음 실행 | 시각 또는 "—" | `CronExpression.next()` |
| 마지막 적재 | 시각 · 결과(완료/실패/일부) · 정상/제외 건수 | `sync_run`/`sync_item` 최신 SUCCESS 또는 최신 실행 |
| API 호출 | 가능 / 불가 (서비스 ID·활성·검증 통과 여부) | 기존 `callable` 계산 |
| 동작 | [API 테스트] [수집 이력] | `/api-test?dataset=...`, 이력 상세 |

위쪽 요약은 숫자 4개만 둔다: 스케줄 설정 N개 · 다음 24시간 내 실행 N개 · 최근 실패 N개 · 호출 불가 N개.

### 4.2 검증: 계약 카드 → 적재 시 자동 검사

현재의 수동 검증 폼은 첫 화면에서 빼고, 검사 자체는 **적재 파이프라인에 넣는다**.

적재 1회마다 다음을 검사한다.

1. 응답에 기대 태그가 있는가 (매퍼가 선언한 필수 태그)
2. 파싱 실패율이 임계값 이하인가
3. 행 수가 0이 아닌가 (0이면 "이동 없음"과 "구조 오류"를 구분해 경고)

검사 결과는 `sync_item`에 기록하고, 실패하면 승격을 막는다. 현재 `readiness`가 하는 역할을 실행 단계로 옮긴 것이다.

**계약 상태(`contract_status`)를 자동으로 `VERIFIED`로 올릴지는 결정이 필요하다** (8절 Q1).

### 4.3 통계: 별도 페이지

`/kras-stats` 신설. 현재 통계 카드 5개와 데이터셋별 행 수를 옮긴다. 메뉴 항목을 하나 추가한다.

### 4.4 API 테스트 연결

각 행의 [API 테스트] 버튼은 `/api-test`를 해당 데이터셋으로 열어 준다. 화면 안에서 바로 호출하지는 않는다. 호출 결과를 행에 표시하려면 "마지막 호출" 열을 추가할 수 있다 (선택).

## 5. 스케줄 설정 방식

신규 경로 데이터셋의 스케줄은 `kras.sync_dataset`에 `schedule_cron` 열을 추가해 데이터셋마다 둔다. 기존 `kras.schedule`과 같은 cron 형식을 쓴다.

- 값이 없으면 "수동"으로 표시한다.
- 스케줄 실행은 기존 `DynamicScheduleManager` 패턴을 따르되, 신규 경로이므로 기존 `SyncScheduler`는 수정하지 않는다 (as-built 문서의 분리 원칙).
- 실행 전 게이트는 현재 `readiness`와 같다 (서비스 ID, 계약 검증, 활성화).

## 6. 구현 범위

| 항목 | 작업 | 위험 |
|---|---|---|
| 첫 화면 표 | 열 구성 재작성, `SPEC_ITEMS` 확장 (파일 데이터셋 포함) | 낮음 |
| 다음/마지막 실행 계산 | `sync_run` 최신 조회 + `CronExpression.next()` | 낮음 |
| 스케줄 열 | `kras.sync_dataset.schedule_cron` 마이그레이션 + 설정 화면 | 중간 (DDL) |
| 통계 페이지 | 신규 `/kras-stats` + 메뉴 | 낮음 |
| 적재 시 검사 | 매퍼 필수 태그 선언 + 파이프라인 검사 단계 | 중간 — 승격 게이트 변경 |
| 수동 검증 폼 | 첫 화면에서 제거, 자동 검사 결과로 대체 | **높음 — Q1 결정 필요** |
| 스케줄 실행 | 데이터셋별 scheduler | 중간 — 운영 DB 부하 |

## 7. 테스트 계획

- 다음 실행 계산: cron별 다음 시각 (경계: 월말, 자정)
- 마지막 실행 표시: 실행 없음 / 성공 / 실패 / 일부 실패
- 적재 검사: 필수 태그 누락 시 승격 차단, 행 수 0 경고 구분
- 화면: 16개 행 렌더링, 스케줄 없음 표시, [API 테스트] 링크 파라미터
- 기존 `KrasIntegrationViewTest`, `KrasSpecItemRowsTest` 갱신

## 8. 결정 (확정 및 구현 상태)

| 항목 | 결정 | 구현 상태 |
|---|---|---|
| Q1 계약 검증 | 자동 검사 + 사람이 VERIFIED 전환 | 검증 폼은 데이터셋 카드(상세 영역의 "데이터셋 카드 열기")에 그대로 있음. **자동 검사 파이프라인은 미구현** |
| Q2 통계 위치 | 별도 페이지 `/kras-stats` | **구현 완료** (`KrasStatsController`, `kras-stats.html`, 메뉴 "KRAS 통계") |
| Q3 정기 실행 | 증분 설계 일정 적용 | **미구현**. 현재 신규 경로는 전부 "수동"으로 표시. land_change는 서비스 ID가 없어 실행 불가 |

첫 화면 운영 열: 스케줄(수동), 다음 실행(—), 마지막 적재(sync_item 최신 건), API 테스트(`/api-test`), 상세.
상단에는 기존 KRAS 동기화(`kras.schedule`)의 다음 실행 시각을 표시한다.

## 8-1. 결정이 필요했던 것 (기록용)

**Q1. 계약 검증을 어떻게 할까?** (가장 중요)
- (a) 적재 시 자동 검사가 통과하면 `VERIFIED`로 자동 전환한다. 사람 확인은 없어진다.
- (b) 자동 검사는 항상 하고, `VERIFIED` 전환은 사람이 한 번 확인한다. 검증 폼은 첫 화면이 아니라 데이터셋 상세에 둔다. **(권장)**
- (c) 검증 폼을 그대로 두고 첫 화면에서만 뺀다.

**Q2. 통계는 어디에 둘까?**
- (a) 별도 페이지 `/kras-stats`를 메뉴에 추가 **(권장)**
- (b) `/kras-db` 하단의 접힌 영역

**Q3. 신규 경로 데이터셋을 정기 실행할까?**
- (a) 지금은 상태만 표시하고 스케줄은 아직 걸지 않는다 (스케줄은 "수동"으로 표시)
- (b) 증분 설계(2026-10-07-kras-incremental-sync-design.md)의 일정을 따른다: `land_basic_file` 월 1회, `land_change` 매일 06:00. `land_change`는 서비스 ID가 없어 호출 불가로 표시된다 **(권장)**
